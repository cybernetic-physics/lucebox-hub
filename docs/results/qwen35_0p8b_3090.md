# Qwen3.5-0.8B RL rollout on RTX 3090 — 3090-train branch

Numbers are best-of-2-runs on a single RTX 3090 (SM86, 82 SMs, 24 GB),
PyTorch 2.11+cu128, transformers 4.48.3 + flash-linear-attention 0.5.0.
Generation length is fixed at 32 tokens after each prompt; prefill is
the cuBLAS+graph path (`prefill_bf16`), decode is the persistent
megakernel.

## Rollout vs HF generate

End-to-end `prefill + 32 generated tokens`, ms wall:

| Prompt | HF (ms) | SGLang (ms) | Ours (ms) | vs HF | vs SGLang |
|-------:|--------:|------------:|----------:|------:|----------:|
|    128 |     971 |         483 |        80 | 12.1× |     6.0×  |
|    512 |    1025 |         478 |        92 | 11.1× |     5.2×  |
|   2048 |    1126 |         507 |       150 |  7.5× |     3.4×  |
|   8192 |    1652 |         668 |       384 |  4.3× |     1.7×  |
|  16384 |    2580 |         926 |       813 |  3.2× |     1.14× |
|  32768 |    4798 |        1254 |      1766 |  2.7× |     0.71× |

Faster than HF generate at every shape and faster than SGLang up to
S=16K. SGLang wins by ~30% at S=32K — its `fla.chunk_gated_delta_rule`
prefill is more efficient than our V-split recurrence at the longest
shapes; closing this is what the parallel-scan DN forward (deferred
from fork-parent-b200's experimental tip) was designed for.

SGLang config: `tp_size=1, mem_fraction_static=0.7, disable_cuda_graph=True,
disable_radix_cache=True, temperature=0.0`. CUDA graphs disabled because
SGLang's mamba/DN backend is incompatible with overlap scheduling. Engine
warmed once before timing; runs=2 averaged.

## What was on the table when this work started

The 3090-train branch had been forked off b200-train and inherited two
B200-specific assumptions that hurt RTX 3090:

1. **One-block-per-qhead FA decode** in `kernel.cu`. Replaced the
   split-K design from fork-parent-b200~2 with a simpler per-qhead
   loop. On B200 (148 SMs) it works because each FA layer also runs
   the rest of the megakernel work in parallel; on 3090 (82 SMs) only
   8 of 82 SMs were busy during the FA scan.

2. **DN V-split block count = 16 × 8 = 128.** Tuned to fully populate
   B200's 148 SMs. On 3090 it forces a second SM wave that pays full
   per-step launch cost again.

Plus `dn_chunked.cu` allocated ~217 KB shared per block (B200's per-SM
limit is 228 KB; RTX 3090's opt-in cap is ~99 KB), so its kernel
launch silently failed.

## What changed on this branch

### 1. Port split-K FA decode from fork-parent-b200~2 (commit 424d865)

The kernel was originally written with split-K — each block owns a
(qhead, kvsplit) pair and writes a partial (max, sum, out) into a
global partials buffer; a reduce phase combines splits per qhead.

Restoring this gave back the long-S decode performance:

| Prompt |   gen ms before |   gen ms after | speedup |
|-------:|----------------:|---------------:|--------:|
|    128 |            72.0 |           72.0 |    1.00 |
|    512 |            73.8 |           69.5 |    1.06 |
|   2048 |            87.2 |           70.5 |    1.24 |
|   8192 |           143.2 |           76.3 |    1.88 |
|  16384 |           219.5 |           86.2 |    2.55 |
|  32768 |           369.9 |          103.9 |    3.56 |

### 2. Auto-scale DN V-split block count (commit d0ea3d3)

`pf_deltanet_recurrence_vsplit_prepped` launches `DN_HEADS *
num_v_splits` blocks per layer. On a 3090 we now pick V_SPLITS=4
(64 blocks; one full wave) instead of 8 (128 blocks; two waves).
B200 still gets V_SPLITS=8.

| Prompt | prefill V=8 (ms) | prefill V=4 (ms) | improvement |
|-------:|-----------------:|-----------------:|------------:|
|    128 |              9.3 |              8.7 |          6% |
|    512 |             30.0 |             25.0 |         17% |
|   2048 |            104.3 |             84.6 |         19% |
|   8192 |            426.4 |            329.7 |         23% |
|  16384 |            904.9 |            770.1 |         15% |
|  32768 |           2027.4 |           1755.4 |         13% |

### 3. Disable broken inference DN chunked routing on SM<90 (commit 424d865)

`dn_hf_patch.py` routed inference at S≤512 to our `dn_chunked_fwd`
kernel which doesn't fit in 99 KB. Set `_OURS_INFER_MAX_S = 0` on
sm<90; we fall through to fla. (To beat fla again at short S on 3090
we need a 3090-tuned chunked variant — tracked.)

### 4. Build / runtime fixes (commit 424d865)

- Rewrote hardcoded `/root/lucebox-hub-b200-train/...` paths in trainer
  helpers to `/home/freiza/lucebox-hub/...` so scripts run on this box.
- Added `experiments/bench_3090_rollout.py` — head vs fork-parent-b200~2
  decoder bench harness, runs each variant in its own subprocess so
  the C extensions don't collide.

## Where the long-S prefill time still goes

torch.profiler at S=32 768 prefill (1.78 s CUDA time):

| Kernel                                   |   ms | share |
|------------------------------------------|-----:|------:|
| `pf_deltanet_recurrence_vsplit_prepped`  |  743 | 41.7% |
| `flash_fwd_kernel` (cuDNN FA-2)          |  455 | 25.5% |
| CUTLASS bf16 GEMMs (cuBLAS-dispatched)   |  392 | 22.0% |
| `pf_bf16_matvec` + small element-wise    |  191 | 10.8% |

The DN sequential recurrence is the dominant remaining cost.
Replacing it with a chunked tensor-core forward (Dv=16 V-split, C=32
chunk size to fit 99 KB shared) is the most attractive next win —
analogous to fla's chunked-delta-rule but cooperating with our
prefill graph instead of fla's dispatch path.

### 5. Raise DN recurrence launch_bounds + default BLK=1024 (commit c45ed92)

The V-split DN recurrence kernel was capped at `__launch_bounds__(512, 1)`
which limited block size to 512 threads. With V_SPLITS=4 the V slice is
32 lanes; at BLK=1024 each warp owns CPW_V=1 j-slot — perfect coverage
with the most warps for latency hiding.

| S       | BLK=512 | BLK=1024 | improvement |
|--------:|--------:|---------:|------------:|
|    2048 |    85.2 |     80.1 |          6% |
|    8192 |   330.2 |    310.1 |          6% |
|   32768 |  1312.8 |   1213.9 |        7.5% |

## Cross-check: head vs each fork-parent-b200~N on RTX 3090

Same harness, prefill ms / gen ms, best of 2 runs. Confirms which
fork-parent-b200 commit each kernel-level fix originally landed in:

| P | head pre/gen | fpb200~5 pre/gen | fpb200~4 pre/gen | fpb200~3 pre/gen | fpb200~2 pre/gen |
|---|---:|---:|---:|---:|---:|
| 128   |  8.5 / 71.6 | 287.4 /  70.3 | 287.1 /  70.2 | 285.3 / 69.3 | 285.4 / 69.3 |
| 512   | 23.1 / 69.2 |1170.8 /  73.3 |1171.0 /  73.4 |1137.6 / 69.1 |1137.3 / 69.2 |
| 2048  | 79.8 / 70.7 |5149.7 /  87.2 |5157.0 /  87.4 |4618.6 / 70.7 |4624.4 / 70.8 |
| 8192  |308.2 / 76.5 |27827 / 142.6 | 27836 / 142.6 |19122 / 76.4  |19136 / 76.4  |

What this proves:

* `~5 → ~4` (split-K FA decode, ed61ab6) is the entire decode-speed
  story at long S (gen at S=8K: 142.6 → 76.4 ms = 1.86×). We already
  inherit it via commit 424d865.
* `~4 → ~3` (port chunked DN, off-by-default) and `~3 → ~2`
  (V-split=4 chunked DN, also off-by-default) ship infrastructure but
  no measurable rollout improvement on this hardware.
* The 38-62× prefill gap between head and any fpb200 variant is
  entirely about head having a batched cuBLAS+graph `prefill_bf16`
  while fpb200 walks `decode_kernel` per prompt token. There is no
  cheaper path on the fpb200 side to borrow.

## Open work

- 3090-tuned chunked DN forward (would attack the 743 ms hotspot at
  S=32K).
- 3090-tuned DN backward (current `dn_bwd.cu` asks for ~196 KB shared
  per block; falls back to fla on training).
- Trainer forward+backward still uses HF+PEFT autograd, OOMs at S≥8K
  on 24 GB. Wiring the existing kernel-driven backward
  (`MEGAKERNEL_USE_KERNEL_BWD=1` heterogeneous path) end-to-end on
  3090 would unlock training at long S.
- SGLang baseline harness (deferred — install complexity).
